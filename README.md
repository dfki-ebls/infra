# DFKI EBLS Infrastructure

NixOS configurations of the hosts in `hosts/<name>`, on top of the option modules in `options`, which declare options together with the config implementing them, and the base config in `modules`.
With `services.caddy.enable`, `options/caddy.nix` serves the vhosts below `custom.rootDomain`, and hosts opt into the profile `profiles/proxmox.nix` for a Proxmox VM guest with its image `<host>-image`.
Hosts enabling `services.llmhop.vllm` get the shared setup of `modules/vllm.nix` and declare their own models.
Every host gets a VM for testing, which disables NVIDIA and, with Caddy enabled, serves the vhosts below `localhost` on port 80.

| Host     | Purpose                                                           |
| -------- | ----------------------------------------------------------------- |
| `raise`  | Proxmox VM serving the RAISE website, Rauthy, Hivegent and RAGold |
| `pythia` | Bare-metal vLLM inference server                                  |

```bash
# local VM of a host for testing
nix run .#raise-vm
nix run .#pythia-vm
# connect to a running VM
ssh -o StrictHostKeychecking=no -o UserKnownHostsFile=/dev/null -A -p 2222 127.0.0.1
# raise's image to deploy
nix build .#raise-image
# installer ISO for bare-metal hosts, see pythia's installation
nix build .#legacyPackages.x86_64-linux.installer.iso-installer
# rebuild on a host, which picks the configuration of its hostname
sudo nixos-rebuild --flake github:dfki-ebls/infra --refresh switch
```

On macOS, the VM of a large closure such as raise needs `sandbox = false`, since the macOS sandbox profile of its launcher, which lists every store path, exceeds 64 KiB.

Every host upgrades itself nightly from `github:dfki-ebls/infra#<host>` and reboots between 04:00 and 05:00 if needed.

## Watermarking

vLLM marks the output of Qwen3.8 with `dual_key_gumbel` (`hosts/<host>/vllm.nix`), the algorithm that supports the MTP speculative decoding these models use, with probabilistic drafting.
`enforce` overrides requests opting out with `watermarking: false`, while greedy requests (`temperature: 0`) still cannot carry a Gumbel watermark.
Deduplication also covers the prompt, since Gumbel sampling is deterministic per context and an agent retrying a failed tool call would otherwise regenerate the identical tokens.
This is vLLM's option for multi-turn non-distortion, at the cost of leaving text copied from the prompt unmarked, and the default 8192-position search window keeps its scanning cost bounded.
The detector `vllm-watermark` shares that config and is reached through llmhop at `/route/watermark/detect`.
Its profile `qwen3.8-27b-gumbel` keeps the plain `gumbel` config used before MTP, so earlier text stays detectable, at the cost of doubling the Bonferroni-corrected p-value.

The key `vllm.watermark-key` is an unsigned 64-bit integer generated by `custom.credstore` and shared by the model and the detector, so changing it makes previously marked text undetectable.
Back it up, and to restore a backup, write it to the same path before the units first start, or replace the file and restart them.

## raise

### VPN allowlist

The `vpnOnly` vhosts of `options/caddy.nix` (`rauthy`, `hivegent`) are restricted to the `client_ip` allowlist in the server-local drop-ins `/etc/caddy/vpn.d/*.caddy`.
Caddy resolves the import when it adapts its config at startup, so the allowlist lives only on the server and changes with a `systemctl restart caddy`, no rebuild.
The vhosts fail closed, so they answer 403 to everyone but loopback on a fresh image or when the drop-ins are missing.

Allow the DFKI VPN ranges by creating `/etc/caddy/vpn.d/allow.caddy`, then restarting Caddy:

```caddy
client_ip 136.199.0.0/16
client_ip 203.0.113.5
```

Each `client_ip` line is merged into one allowlist, so add or remove entries one per line.
Ranges and bare IPs are accepted interchangeably, so `203.0.113.5` allows that single host alongside the range.

### Rauthy

Rauthy is the OIDC identity provider.
Encryption and cluster secrets are generated on first start into the credential `/etc/credstore/rauthy.secrets`.
Rauthy encrypts data with that key, so regenerating it makes existing data unreadable.

User-managed secrets live in `/etc/rauthy/rauthy.env`, whose entries override the secrets file.
Rauthy sends mail through the uni Trier relay (`mail.wi2.uni-trier.de:465`, implicit TLS), and the SMTP password is the only secret kept out of the Nix store.
Provision it on the server, then restart:

```bash
printf 'SMTP_PASSWORD=%s\n' '<secret>' > /etc/rauthy/rauthy.env
systemctl restart rauthy
```

### Hivegent

Hivegent keeps its state in a local Postgres database shared with Rauthy.
It re-applies its Alembic migrations on every startup, so dropping the database is enough to start over.

Stop the backend, drop and recreate an empty database owned by the `hivegent` role, then start it again:

```bash
systemctl stop hivegent
sudo -u postgres psql \
  -c 'DROP DATABASE hivegent WITH (FORCE);' \
  -c 'CREATE DATABASE hivegent OWNER hivegent;'
systemctl start hivegent
```

Do not restart the `postgresql` service, since Rauthy shares the same instance.
To also wipe local files for a full reset, clear the state and cache while stopped: `rm -rf /var/lib/hivegent/* /var/cache/hivegent/*`.

Runtime secrets are systemd credentials named after their component, and the unit imports every `hivegent.*` credential from the system credential store.
Hivegent maps `hivegent.<NAME>` to the setting of the variable `HIVEGENT_<NAME>`, so any setting can be a credential, while llmhop names its credentials after their `${cred:…}` references.
Secrets listed in `custom.credstore` (`options/credstore.nix`) are generated if missing, before the first service importing them starts.
Store any other one as a plain file in `/etc/credstore`, which systemd keeps readable by root only, and restart:

```bash
(umask 077; systemd-ask-password -n "MCP client secret:" > /etc/credstore/hivegent.MCP__CLIENT_SECRET)
systemctl restart hivegent
```

List the credentials the unit receives, without printing their values:

```bash
systemd-run --pipe --wait --quiet --property=ImportCredential='hivegent.*' systemd-creds list
```

Remove a secret by deleting its file and restarting.

#### Hardening

- The API accepts tokens only of the exact clients `hivegent-spa` and `hivegent-integration`.
- Caddy enforces a Content Security Policy on the SPA that allows images, fetches, and frames only from the vhost itself, `blob:`/`data:` URLs, and Rauthy, so model output cannot exfiltrate data through remote images.
  Future work: the policy does not restrict scripts yet, so it should add `script-src 'self'` with the hash of the inline script of `index.html`, or move that script into a file, plus `object-src 'none'` and `default-src 'none'` with the remaining fetch directives.
  The `Content-Security-Policy` set inside `handle /api/*` is redundant, since the deferred `@csp_api` header replaces it.
- The backend unit runs without host devices, since the GPU is hidden from it.
- Postgres listens only on its unix socket, and each service role may connect only to the database of the same name.

#### Watermarking

Hivegent's `transparency` section points at the [watermark](#watermarking) detector of raise's own llmhop.
llmhop listens only on the unix socket `/run/llmhop/default.sock` (`hosts/raise/llmhop.nix`), which only members of the `llmhop` group can use, so no other local process can request unmarked output.
Hivegent's dynamic user joins that group through `SupplementaryGroups`.
Hivegent derives the key that signs detection reports and export provenance from `hivegent.TRANSPARENCY__SECRET_KEY`, generated by `custom.credstore`, so changing it rotates that key.
Back it up like the watermark key, and see Hivegent's `docs/article-50-2-operations.md` for rotation and testing.

#### Service integrations (client credentials)

The browser SPA client (`hivegent-spa`) is provisioned automatically on first DB init.
To let an external service call the API non-interactively, create a confidential client by hand in the Rauthy admin UI so its secret stays out of the Nix store.
In **Clients → Add Client** set:

- **Client ID**: `hivegent-integration`, since Hivegent accepts tokens only for the client ids listed in its `auth.audience` (`hosts/raise/hivegent.nix`), so another id needs adding there first.
- **Confidential**: yes, since the client credentials grant requires a secret; copy the generated secret, as it is shown only once.
- **Enabled flows**: `client_credentials` only, with no redirect URIs.
- **Token algorithm**: EdDSA for both the access and ID token.
- **Scopes**: `openid` is enough; a client-credentials token carries no user, so it has no `groups` claim and the integration operates only on its own knowledge namespace (`user:hivegent-integration`), never shared group knowledge.

`access.client_credentials_map_sub` is already enabled in the Rauthy config, so the token's `sub` is the client id, which becomes the integration's identity in Hivegent.
The client secret is long lived until rotated, deleted, or the client is disabled.
Each returned bearer token is short lived and the token response includes `expires_in`.
The default token lifetime for a newly created Rauthy client is 1800 seconds unless changed in the client settings.

Fetch a token and call the API:

```bash
token=$(curl -fsS https://sso.<domain>/auth/v1/oidc/token \
  -d grant_type=client_credentials \
  -d client_id=hivegent-integration \
  -d client_secret=<secret> | jq -r .access_token)

curl -fsS https://hivegent.<domain>/api/v1/directories/~ -H "Authorization: Bearer $token"
```

For Python services, cache the token and refresh it shortly before it expires:

```python
from dataclasses import dataclass
from time import monotonic

import httpx


@dataclass(slots=True)
class ClientCredentialsAuth:
    token_url: str
    client_id: str
    client_secret: str
    access_token: str | None = None
    expires_at: float = 0.0

    async def headers(self, client: httpx.AsyncClient) -> dict[str, str]:
        access_token = self.access_token
        if access_token is None or monotonic() >= self.expires_at - 60:
            response = await client.post(
                self.token_url,
                data={
                    "grant_type": "client_credentials",
                    "client_id": self.client_id,
                    "client_secret": self.client_secret,
                },
                timeout=10,
            )
            response.raise_for_status()
            token = response.json()
            access_token = str(token["access_token"])
            self.access_token = access_token
            self.expires_at = monotonic() + int(token["expires_in"])

        return {"Authorization": f"Bearer {access_token}"}


async def get_workspace_tree(client: httpx.AsyncClient, auth: ClientCredentialsAuth) -> object:
    response = await client.get(
        "https://hivegent.<domain>/api/v1/directories/~",
        headers=await auth.headers(client),
    )
    response.raise_for_status()
    return response.json()
```

Any service that already depends on Authlib can use its HTTPX OAuth client instead:
When the client stays open, Authlib renews expired client credentials tokens from `token_endpoint` before protected requests.

```python
from authlib.integrations.httpx_client import AsyncOAuth2Client


async def get_workspace_tree() -> object:
    async with AsyncOAuth2Client(
        "hivegent-integration",
        "<secret>",
        token_endpoint="https://sso.<domain>/auth/v1/oidc/token",
        token_endpoint_auth_method="client_secret_post",
    ) as client:
        await client.fetch_token(grant_type="client_credentials")
        response = await client.get("https://hivegent.<domain>/api/v1/directories/~")
        response.raise_for_status()
        return response.json()
```

Rotate the secret from the same admin UI screen; nothing in the Nix store needs to change.

## pythia

raise keeps serving its own model on its RTX PRO 4500 until Hivegent moves to pythia, which then needs pointing at `https://pythia.dfki.uni-trier.de` with a token from `llmhopctl token create hivegent`.

ASUS Pro WS WRX90E-SAGE SE with an AMD Threadripper PRO 9975WX, 256 GB ECC RAM, two RTX PRO 6000 Blackwell Workstation Edition cards for Qwen3.8 and an RTX PRO 6000 Blackwell Max-Q for the embedding and OCR models.

### Disks

The two SSDs each hold an ESP and a ZFS partition, which form a mirror (`hosts/pythia/disk.nix`).
GRUB installs itself into both ESPs, with a firmware boot entry for each, so either SSD boots on its own.
If one fails, the initrd waits for it briefly and then imports the pool degraded, without manual intervention.
vLLM's cache has its own dataset `zroot/vllm`, which keeps the weights out of the ARC since the page cache already holds them.
The empty dataset `zroot/reserved` holds back 50 GB, so that a full pool can still delete files after `zfs set refreservation=none zroot/reserved`.
disko's `format` mode also applies dataset changes to the running system, creating missing datasets and setting changed properties, which take effect after a reboot or `nixos-rebuild switch` mounts them.

### Installation

Build the installer image, which accepts the admin's SSH keys for `root`, and write it to a USB stick:

```bash
nix build .#legacyPackages.x86_64-linux.installer.iso-installer
sudo dd if=result/iso/nixos-*.iso of=/dev/<usb> bs=4M status=progress oflag=sync
```

Boot pythia from it and connect with `ssh root@<ip>`.
Replace the placeholder disk paths in `hosts/pythia/disk.nix` with the SSDs' entries in `/dev/disk/by-id`.
Then partition, format, and install:

```bash
sudo nix run github:nix-community/disko/latest -- --mode destroy,format,mount --flake github:dfki-ebls/infra#pythia
sudo nixos-install --flake github:dfki-ebls/infra#pythia --no-root-passwd
```

After the first boot, replace the GPU indices in `hosts/pythia/vllm.nix` with the positions of the three RTX PRO 6000 in PCI bus order, counting from 0, which `nvidia-smi --query-gpu=pci.bus_id,name --format=csv,noheader | sort` lists.
The indices follow the slots, so moving a card to another slot moves the models with it.

### Disk replacement

Put the new SSD's entry in `/dev/disk/by-id` into `hosts/pythia/disk.nix`.
disko's `format` mode then partitions and formats only that SSD, since it leaves existing partition tables, file systems, and pools alone.
Replace the missing mirror half with the new partition and reinstall the bootloader into both ESPs:

```bash
sudo nix run github:nix-community/disko/latest -- --mode format --flake .#pythia
sudo zpool replace zroot <missing-vdev> /dev/disk/by-partlabel/disk-b-zfs
sudo mount /boot-fallback && sudo nixos-rebuild boot --install-bootloader
```

Use `disk-a-zfs` and `/boot` if the first SSD failed, and take `<missing-vdev>` from `zpool status`.

### Certificate

With `custom.installedCertificates`, Caddy serves the certificate files `/etc/credstore/caddy.tls.cert`, holding the full chain, and `/etc/credstore/caddy.tls.key`, which only root can read.
Install a new certificate, also when renewing, then restart Caddy:

```bash
sudo install -m 600 pythia.crt /etc/credstore/caddy.tls.cert
sudo install -m 600 pythia.key /etc/credstore/caddy.tls.key
sudo systemctl restart caddy
```

### Clients

Caddy serves llmhop's models over TLS at `https://pythia.dfki.uni-trier.de` (`hosts/pythia/llmhop.nix`), proxying to llmhop's unix socket, and each client authenticates with its own bearer token.
The models are `qwen3.8-27b` for chat, `qwen3-embedding-4b` for embeddings, whose queries take the prefix `Instruct: <task>\nQuery:` while documents take none, and `lightonocr-3-4b` for OCR, which turns one page image per chat completion into Markdown, with layout boxes if the text is `grounding`.
Docling's `lightonocr3_4b` preset reaches it through its API engine with the `model` param set to `lightonocr-3-4b`.
Every credential named `llmhop.token.<client>` in `/etc/credstore` is a token, which llmhop reads at startup and on `systemctl reload llmhop`, without a restart.
`llmhopctl` manages the tokens, reloading llmhop and printing new ones:

```bash
sudo llmhopctl token list
sudo llmhopctl token create <client>
sudo llmhopctl token rotate <client>
sudo llmhopctl token revoke <client>
```

If the config fails to load, llmhop keeps the previous one and logs the error.
Without any token, llmhop rejects every request rather than serving it unauthenticated.

### Chat

[BearChat](https://github.com/mirkolenz/bearchat) serves a chat interface for `qwen3.8-27b` at `https://pythia.dfki.uni-trier.de/chat` (`hosts/pythia/bearchat.nix`).
Users sign in with an llmhop token, created like any other client's, which Caddy keeps in an `HttpOnly` cookie, so revoking the token also ends their session.
Chats stay in the browser, so the server keeps no history.

### Watermarking

Only `qwen3.8-27b` is watermarked, see [watermarking](#watermarking), since the embedding model produces no text and the OCR model only transcribes documents.
